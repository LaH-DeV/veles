19. (2026-09-17, user idea, decided "figure out and note") Package surface in source instead of
   the manifest's `exports`:
   - `pub` inside a module = visible to the rest of the package (already the rule, M5).
   - The root module (`lib.vs` by convention; any file of the root directory) re-exports with
     `pub use geometry` — that, and only that, is what other packages may import. Manifest
     `exports` goes away (bootstrap has no users; no compatibility alias needed).
   Design worked out so far:
   - Forms mirror `use`: `pub use geometry` re-exports the module under its name (outsiders write
     `use mathlib.geometry`, as today); `pub use geometry.{ area, Circle }` flattens those items
     into the root (`use mathlib` → `mathlib.area`) — a facade that hides the internal layout,
     which the manifest list cannot do; `pub use geometry as geo` renames.
   - Uniform rule, no root special case: `pub use` in ANY module adds the named module/items to
     that module's pub surface; the root module's pub surface is the package's.
   - Only the package's own modules/items may be re-exported; re-exporting a dependency
     (`pub use utils.text`) is refused for now (keeps "nothing escapes except through the root",
     avoids diamond questions). Revisit when M7 lands.
   - M1 is untouched: the dependency graph still comes from manifests only. The loader parses a
     dependency's root module (its `use` lines) to learn the surface before resolving
     `use dep.mod`; error text: "module 'geometry' of package 'mathlib' is not re-exported; add
     `pub use geometry` to its root module".
   - `pub use` is a `use` edge for M4 cycle detection. Flattened names collide with root decls
     like duplicate declarations. LSP definition/hover follow a re-export to the original.
   - Fits #17: if `.veles` replaces the manifest, identity/deps live there and the surface stays
     in code. Cost: small (loader + checker + LSP), one docs chapter, examples/packages update.

20. (2026-09-18, idea, not yet) Lint: a `mut fun` called on a temporary value struct.
   The situation, step by step:
   - A struct is a VALUE (D7): passing it around copies it, like an i64. A List is a
     REFERENCE (D25): copying the handle still points at the same elements.
   - `m.get(k)` on a `Map<string, Counter>` returns a COPY of the Counter (a `Counter?`), not
     the one stored in the map. Same for `makeCounter()`, `xs.first()` on a plain List, a
     `val c = m.get(k)` read, etc. — any expression that produces a struct value rather than
     naming storage produces a copy.
   - A `mut fun` (e.g. `bump()`) mutates whatever it is called on. Called on a copy, it
     mutates the copy; the copy is then thrown away, so nothing observable happens:
       m.get("a")?.bump()     // compiles, runs, changes nothing — the map still holds n=0
       makeCounter().bump()   // same: the fresh Counter is bumped and dropped
   - This is not a bug in the compiler: the rule "a temporary mutates a fresh copy" is what
     makes iterator chains work (`xs.iter().filter(..).next()` mutates the temporary iterator
     and USES the result). The difference is whether the RESULT is used.
   - `xs.atOrPanic(i)` and `xs.at(i)?.` are special-cased to be PLACES (they name the storage
     inside the list), which is why `counters.at(1)?.bump()` does stick. Maps have no such
     form: a map value is not addressable today.
   The lint: when a `mut fun` that returns NOTHING (unit) is called on a receiver that is
   not a place (a call result, a `?.` on a non-list, a literal) and the receiver's type is a
   value struct (not a List/Map/Set/Channel, which are references), warn:
     "'bump' mutates a temporary copy of 'Counter' that is then discarded; bind it first
      (`var c = m.get("a") ?: ...; c.bump(); m.set("a", c)`)".
   Unit-returning is the key filter: a mut method that returns something (`next()`) is
   presumably called for its result and stays silent. Effort: half a day in `callMethod`

   addressable instead (`m.getOrPanic(k).bump()` in place, like lists)? That would need a
   `map.ref` runtime primitive and would make the lint mostly moot for maps.
